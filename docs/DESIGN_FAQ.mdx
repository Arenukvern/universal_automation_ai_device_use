## Platform tiers (honest today)

**Q: What is the macOS “computer use” tier really?**  
A: **Preview**, not production-hardened desktop control. `universal_driver_macos` implements AX/CGEvent paths; toolkit MCP exposes `serve --os` and related tools. GitHub release binaries are **ad-hoc signed only** until Apple Developer signing is wired — [RELEASING.md](https://github.com/Arenukvern/universal_automation_ai_device_use/blob/main/RELEASING.md#macos-code-signing-optional-not-configured-yet). Unsigned host binaries **lose TCC grants** (Accessibility, Screen Recording) after each toolkit update; users must re-grant. Do not claim stable unattended macOS agent control.

**Q: Why does browser automation attach instead of launching Chrome?**  
A: Target lifecycle belongs to the **host** (oka / your supervisor), not UA. `universal_browser_cdp` discovers and attaches to an **existing** CDP endpoint (`CdpBrowserSession.attach`); it does not spawn browsers. Keeps one observe/act contract while respecting who owns the process ([CDP README](https://github.com/Arenukvern/universal_automation_ai_device_use/blob/main/pkgs/universal_browser_cdp/README.md)).

**Q: Where are Android and iOS?**  
A: **Roadmap only** in this repo. [ADR 0009](/decisions/0009_one_mcp_server_with_adapters) declares factory slots and `oka_devices` handoff — no shipped mobile adapters yet. Do not document or market mobile device-use as available here.

**Q: What does Linux desktop support mean today?**  
A: **AT-SPI read + semantic click** (`Action.DoAction`) via D-Bus — no keyboard synthesis, typing ladder, or browser navigation in `universal_driver_linux` ([driver README](https://github.com/Arenukvern/universal_automation_ai_device_use/blob/main/pkgs/universal_driver_linux/README.md)). Live GNOME proof is still thin; conformance runs against stubs.

**Q: What about Windows?**  
A: The **UIA Rust sidecar is not shipped** as a release artifact consumers can rely on. Dart protocol + stub/conformance exist; live Windows UIA verification is pending ([Windows driver README](https://github.com/Arenukvern/universal_automation_ai_device_use/blob/main/pkgs/universal_driver_windows/README.md)). Toolkit refuses loudly without the sidecar binary.

## Architecture

**Q: Why one MCP server with adapters instead of per-platform servers?**  
A: One **`automation_*` tool surface** and registry; new tiers register **adapter packages** (`universal_driver_*`, `universal_browser_*`, …), never a second MCP product. Honest `tools/list` visibility only when an adapter is installed **and** its target is reachable ([ADR 0009](/decisions/0009_one_mcp_server_with_adapters)).

**Q: Why split `universal_automation_toolkit` and `universal_automation_harness`?**  
A: **Toolkit** = plan runner, MCP/CLI, adapters, low-level composition. **Harness** = composition-root SDK (flows, commands, budgets) that compiles to the **same** `AutomationPlan` artifact every face runs ([ADR 0004](/decisions/0004_harness_layer_and_packaging_boundaries)). Avoids parallel Dart vocabularies and keeps MCP thin.

**Q: Why keep contracts in `universal_automation_interface` separate from drivers?**  
A: Published contracts and conformance travel ahead of platform proof. Drivers opt into the family `AutomationDriver` shape; semantics and refusal behavior stay shared ([ADR 0001](/decisions/0001_drivers_into_ua_private_oss_ready)).

## Release train and workspace policy

**Q: Why Release Please instead of hand-cut versions?**  
A: **Zero-touch release** on `main`: conventional commits bump per-package versions, open a release PR, sync constraints, build toolkit binaries, publish pub.dev — documented in [RELEASING.md](https://github.com/Arenukvern/universal_automation_ai_device_use/blob/main/RELEASING.md). Manual `version:` / `CHANGELOG` edits on releasable packages fight the train.

**Q: Why caret-floor constraint sync instead of always rewriting `^sibling`?**  
A: `tool/sync_workspace_pub_constraints.dart` raises a sibling `^` floor **only** when pub caret semantics no longer admit the new workspace version; patch bumps within range stay untouched; hand-raised floors are never lowered (`--check` fails on drift above sibling). Avoids forced fake co-releases (e.g. harness **0.3.3** only to satisfy a blind pin when **0.3.2** already fits the train). Policy: [RELEASING.md § constraint sync](https://github.com/Arenukvern/universal_automation_ai_device_use/blob/main/RELEASING.md#release-please-constraint-sync) (landed via PR #62).

**Q: Why no git worktrees for agent/CI work on this repo?**  
A: **Policy:** use normal feature branches on a single checkout (`git checkout -b cursor/...`). Worktrees duplicate state, confuse sparse release tooling paths, and make steward/evidence paths harder to reason about. Cloud agents and humans branch from `main` only — not a git technical limitation.
